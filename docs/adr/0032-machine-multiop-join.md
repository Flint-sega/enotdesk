# 0032. Мультиоператор машинных сеансов: join-пароль от claim + автор в чате операторов

Дата: 2026-10-16. Статус: принят (волна G). Наследует: 0030 (pc-per-operator,
арбитраж, cap), волну v0.6.2 (join по ID+паролю, session_operators, from/to-адресация).

## Контекст

Приёмка волны C (16.10) вскрыла архитектурный пробел: второй оператор не мог
присоединиться к МАШИННОМУ сеансу — claim машины эксклюзивен (409 machine_busy),
пароль machine-сеанса генерировался, но никому не выдавался, join-ветка
`/sessions/:id/claim` была недостижима. Вся хостовая механика мультиопера
(волна C) при этом была готова. Попутно: wire-протокол чата `{type:'chat',text}`
не нёс автора — на принимающей стороне сообщение другого оператора
подписывалось «Клиент:».

## Решение

1. **Машинный claim отдаёт join-пароль.** `POST /machines/:id/claim` включает
   `password` сеанса в ответ оператору-владельцу (RBAC маршрута — operator/admin;
   в БД по-прежнему только хеш, в audit пароль не пишется). Дальше коллега
   подключается СУЩЕСТВУЮЩИМ attended-путём: join-форма ID+пароль →
   `POST /sessions/:id/claim {password}` → session_operators → WS. Никаких новых
   сущностей, эндинпойнтов или состояний: решение — выдача одного поля.
   Join-ответ дополнительно несёт `machineId` (UI понимает контекст машины);
   хост получает `operator-joined` с именем коллеги (уже было).
2. **Web-карточка «Подключение коллег»** после успешного machine-claim: ID+пароль,
   копирование кликом через выделение (`user-select:all`) — без clipboard-API
   (SEC-002). Карточка гасится при выходе из сеанса.
3. **Автор в чате — мягкое расширение провода.** Разрешены необязательные
   `from ∈ {operator, host}` и `name` (строка 1..120): парсер толерантен к
   легаси-проводу (без полей = «Клиент:» на новых получателях), мусорные
   значения отбрасываются ПОЛЯМИ, не сообщением. Метку ставит ТОЛЬКО
   хост-релей (attended renderer и машинный агент): входящая `from` от
   оператора перезаписывается реальным автором — спуф «я — хост» невозможен
   **при хосте ≥ 0.6.21** (закреплено тестами). Переходное окно микса версий:
   старый хост (0.6.20) релеит чат операторов сырым проводом без перезаписи —
   новые операторы-получатели отрисуют неперезаписанные `from/name` как есть;
   подпись автора в чате — доверенная только при обновлённом хосте (клиент и
   агент автообновляются, окно самозакрывается). Подписи: «Оператор {имя}:» /
   «Клиент:».

## Альтернативы

- Мульти-claim машины по роли (любой operator заходит без пароля): отвергнуто —
  скрытное подключение к чужому сеансу без ведома владельца; пароль делает акт
  явным (владелец осознанно передаёт).
- Новый эндпоинт «присоединиться к machine-сеансу»: отвергнуто — дублировал бы
  существующий join-путь ради другого способа аутентификации.
- Поле автора в validateInput-подобном строгом парсере с мажоритацией провода:
  отвергнуто — мягкий allowlist + перезапись метки на хосте дают совместимость
  без версии протокола.

## Последствия

+ Второй и последующие операторы получают полный доступ к machine-сеансу
  (видео/терминал-по-очереди/чат/файлы/ввод по арбитражу) — M2–M4 становятся
  достижимы; диф сервера минимален.
+ Чат операторов читаем; хост всегда отличим; старые узлы не ломаются.
− Пароль machine-сеанса виден владельцу claim'а в UI (как пароль attended-сеанса
  хосту) — осознанная симметрия доверия; перехват чужого пароля по-прежнему
  не даёт ввода без арбитража.
− Микс версий 0.6.20-хост + 0.6.21-оператор: `from/name` проходят к получателю
  неперезаписанными (старый релей сырой провод) — подпись автора в переходном
  окне не доверенная; при гомогенной 0.6.21 гарантии полные, окно закрывается
  автообновлением хостов (ревью Рината P2-1).
− Join по паролю machine-сеанса — web-оператор; desktop-оператор machine-сеанс
  не офферит (прежденяя граница MANUAL-QA), его join зависнет во взаимном
  ожидании — документировать в подсказке карточки (решение о desktop-офферинге —
  владелец; ревью P3-2).
