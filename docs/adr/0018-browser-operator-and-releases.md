# ADR 0018: браузерный оператор /operator переиспользует client/lib-протоколы (новый код — только DOM→протокол); релизы — electron-updater на GitHub Releases с checksums, неподписанные сборки с инструкциями; Windows portable — только уведомление

## Контекст

R05/R17i/R07: оператор должен работать без установки desktop-клиента — открыть `/operator` в Chrome, войти тем же аккаунтом; релизы выходят на GitHub Releases, клиент сам сообщает об обновлении; бюджета на сертификаты подписи нет (R07: «подписываем сами чтоб работало»). При этом протоколы (input allowlist, chat/clip/file DC-каналы, WS-состояния обрыва) уже реализованы в `client/lib/*` и allowlist-нуты, CSP на сервере уже есть.

## Решение

Браузерный оператор — статическая страница, которую отдаёт существующий сервер на `/operator`; переиспользует модули рендерера и `client/lib/*` как ES-модули, без бандлера. Новый код — только источник DOM-событий `web/input-source.mjs` (`wireBrowserInput(video, send, {keys})`: pointer/wheel/keyboard → те же allowlist-события протокола, раскладка по e.code) и логин-форма. Чат, буфер и файлы — через те же DC-каналы (Clipboard API, file input/drag&drop); RBAC тот же (auditor — только чтение, чужие операции — 403); состояния обрыва — те же WS-сообщения (peer-reconnecting, resumed, ended). Релизы: electron-updater (generic-провайдер по URL GitHub Releases, в dev отключён, парсер фида покрыт тестом); workflow release.yml по тегу `v…` собирает 3 платформы и прикладывает артефакты с SHA256-checksums; секреты подписи — закомментированный блок в workflow. Неподписанные сборки запускаются по коротким инструкциям в README и описании релиза: macOS ПКМ→Открыть, Windows SmartScreen «Выполнить в любом случае», Linux `chmod +x`.

## Почему

Второй веб-клиент со своей реализацией протокола — отвергнуто: дубль allowlist-логики — второй источник дыр, а расхождение desktop и web не поймать без общей базы; единственный новый шов (DOM→протокол) закрывается тестом «события по форме идентичны desktop-протоколу». Бандлер (vite/webpack) — отвергнуто: ES-модули уже работают и в Electron, и в Chrome, CSP уже настроен — бандлер добавил бы сборочный шаг без новой возможности. Свой update-сервер — отвергнуто: electron-updater + GitHub Releases покрывают проверку, уведомление и скачивание без инфраструктуры. Подпись сертификатами сейчас — отвергнуто (нет бюджета): вместо фейкового доверия — честные инструкции обхода предупреждений; закомментированный блок в release.yml превращает будущую подпись в добавление секретов, а не переделку. Windows portable: авто-обновление в один клик для portable-сборки невозможно — она честно получает только уведомление о новой версии, обновление руками.

## Последствия

Паритет браузера с desktop — по списку главных сценариев в доке, и отличия браузера перечислены честно, а не «всё как в desktop» (например, Clipboard API зависит от браузера и выданных прав страницы). `web/input-source.mjs` — единственное место, где web-путь может разойтись с desktop, поэтому контракт-тест на трансляцию обязателен и расширяется на словари. GitHub Releases — единственный канал обновлений: первый push и публикация релиза тегом — наружные действия только по явной команде пользователя; до тега updater-фид не существует, «обновления» в dev отключены — ложных срабатываний нет. Неподписанные сборки: предупреждения SmartScreen/Gatekeeper — норма, задокументированная в README и релизе, а не баг; включение подписи позже — вставка секретов в готовый блок. Аудитором интеграция не проверяется отдельно: RBAC тот же серверный, веб-клиент не получает больше прав, чем роль.
