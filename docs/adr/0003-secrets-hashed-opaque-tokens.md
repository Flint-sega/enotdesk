# ADR 0003: все секреты только хешами, opaque-токены вместо JWT

## Контекст

В системе есть несколько классов долгоживущих секретов: пароли операторов, hostToken, bearer-токены сессий, одноразовые invite-ссылки. Сервер переживает рестарт, аудит обязателен, утечка дампа БД недопустима как сценарий раскрытия доступа.

## Решение

Пароли — salted scrypt; hostToken, операторские bearer и invite-токены хранятся в БД только как хеши, у клиентов существуют только в памяти; invite одноразовый, accept атомарен, revoke по хешу. Bearer-токены opaque (случайные, с серверным состоянием), TTL 8 часов, logout отзывает немедленно.

## Почему

Рассмотрен JWT/stateless-токен: отвергнут — требуемые немедленный отзыв при disable/logout и закрытие живых WS-подключений по актуальной роли вынуждают вести серверное состояние, и JWT вырождается в opaque с лишней криптографией и окном отзыва. Рассмотрено хранение токенов открытым текстом: отвергнуто — дамп БД или лог давал бы готовый доступ ко всем сеансам и приглашениям; хеширование делает утечку хранилища бесполезной для входа.

## Последствия

Каждая проверка токена — lookup в SQLite (индекс по хешу), а не локальная проверка подписи; при масштабе одной команды это неощутимо. Восстановить «потерянный» invite или токен невозможно — только выпустить новый. Рестарт сервера с чистым состоянием сессий (см. спецификацию) обязан оставить хеши учётных записей и аудита нетронутыми — схема хранения попадает в миграции и тесты на персистентность.
