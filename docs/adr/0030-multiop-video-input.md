# 0030. Мультиоператор: видео и ввод для всех присоединившихся (pc-per-operator в attended и в машинном мосту; явный арбитраж ввода; cap видеослотов)

Дата: 2026-10-15. Статус: принят (волна C, реализация по плану ultra от 15.10).
Наследует: 0014 (сервисы по DataChannel), 0021 (машинный мост/терминал), 0027 (unattended
видео), волну v0.4.0 (мультиоператорский join) и коммит 0d191f9 (волна 1, pc-per-operator
attended-хост).

## Контекст

Сервер релеит сигналинг адресно (to=claimId host→оп, from=claimId оп→host) и оповещает
хост об operator-joined/left — с v0.6.2. Но: (1) машинный сеанс держит ОДИН pc в скрытом
мосту — второй браузерный оператор не получает видео/ввод/терминал и ломает ренеготиации
первого (bridge.mjs `if (pc) return` молча глотает второй offer, createAnswer виснет,
answer уходит fan-out'ом); (2) ввод всех операторов миксуется в одну очередь инъекции
(last-write-wins) — одновременный ввод двух операторов недетерминирован и опасен;
(3) нет потолка числа pc — память/CPU хоста расходуются без ограничений.

## Решение

1. **Attended-хост: pc-per-operator** (уже в коде с волны 1) — ретро-документируем:
   захваченный track расшаривается в персональный pc каждого оператора, offer
   адресуется `to:claimId`, answer/ICE оператора роутятся по `from`. Каналы
   input/chat/clip/file создаются per-operator (ADR 0014). Adaptive-bitrate —
   per-viewer: у каждого pc свой энкодер и свой цикл ступеней
   (client/lib/adaptive-bitrate.mjs, применено в session-media.js startAdaptive).
2. **Машинный путь: N pc в ОДНОМ окне моста.** Мост остаётся один (скрытое
   BrowserWindow), внутри — Map<claimId, pc>. IPC-каналы BRIDGE_IPC не меняются
   (имена захардкожены в sandbox-preload), адресация — полем `op` в payload
   (отсутствие `op` = 'primary' — обратная совместимость шимов/тестов).
   Видео: JPEG-кадры хелпера рисуются на ОДИН canvas, один canvas.captureStream-track
   расшаривается replaceTrack'ом в видеотрансивер каждого pc (аналог одного
   localStream в N pc attended-хоста). Терминал — один на машину (граница v1):
   первый открывший работает, второй получает честный отказ term-busy.
   Answer/ICE агента адресуются `to:claimId` (откуда взяли `from`). Оффер от
   неизвестного/чужого claimId при живом pc — честный игнор с логом (W-C1:
   второй оператор больше НЕ ломает первый machine-сеанс даже без N pc).
3. **Арбитраж ввода — явный захват с авто-выдачей одинокому.** Состояние
   «активный вводчик» живёт в main (конвенция: решение о вводе — только main),
   чистый модуль client/lib/input-arbiter.mjs. Правила: (а) пока оператор один —
   ввод его (сессия одного оператора ведёт себя как раньше, без регресса UX);
   (б) при >1 ввод имеет только захвативший: оператор шлёт по input-DC служебное
   `{"type":"claim-input"}` / `{"type":"release-input"}`, хост переключает активного
   и рассылает всем `{"type":"input-grant","granted":true|false}` по их input-DC;
   (в) уход/обрыв pc активного освобождает ввод (arbiter.drop), повторный захват —
   любым; release/drop активного НЕ передаёт ввод автоматически (детерминизм:
   следующий получает только по своей явной кнопке). События ввода не-активного
   оператора отбрасываются в main до инъекции; idle-таймер считает только
   разрешённые. UI операторов: кнопка «Взять управление»/«Отдать управление» +
   честный статус «Управление/Просмотр» (desktop и web-оператор).
   Не выбрано: «последний вводивший за N сек» (драка курсором, случайные перехваты —
   реальные инциденты поддержки) и «ввод всем всегда» (текущий last-write-wins —
   недетерминирован).
4. **Cap видеослотов: 3.** Константа MULTIOP_VIDEO_CAP=3 (client/lib/multiop-limits.mjs,
   решение — чистая videoAllowed(count, cap)). Присоединение свыше: pc строится БЕЗ
   видеотрека (attended) / с видеотрансивером inactive (машина) — чат/файлы/терминал
   работают, по input-DC оператору приходит `{"type":"session-info","video":false,
   "reason":"video-slots-full"}` и UI честно показывает «Видеослоты заняты».
   Cap на join НЕ вводим: чат-участие без видео полезно и безопасно, сервер не трогаем.
5. **Сервер не меняется.** Адресация to/from, operator-joined/left и replay уже есть
   (server/app.mjs: operator-joined при WS-подключении, operator-left при уходе,
   replay после reconnect хоста; `to` = адресно, без `to` = fan-out, `from` на
   op→host сигнале).

## Альтернативы

- Окно-мост × N (по окну на оператора): отвергнуто — ipcMain-каналы BRIDGE_IPC
  глобальные, имена не параметризовать без смены preload; память окна × N.
- Смена оферера на машине (агент офферит, как attended): отвергнуто — ломает
  ренеготиацию терминала оператора (onnegotiationneeded) и весь существующий
  веб-путь; диф больше.
- Серверный join-cap (409 при >3): не нужен для цели волны; защитить хост — забота
  хоста (см. п.4).
- Implicit-арбитраж «активный = последний вводивший за N сек»: отвергнут —
  непредсказуем для живого человека за удалённым столом.

## Последствия

+ Второй и последующие операторы получают видео, ввод (по захвату), чат, файлы,
  терминал (первый занявший) в обоих типах сеансов; сервер и протокол /signal —
  без изменений.
+ Память/CPU хоста ограничены cap'ом; деградация честная (статус, не таймаут).
− N энкодеров на хосте: CPU растёт с числом операторов (замер в приёмке;
  при 3×2.5 Мбит/с — ожидаемо на уровне обычного WebRTC-кодирования).
− Старый оператор (≤0.6.19) при >1 операторов не понимает input-grant и не знает,
  что ввод заблокирован (события молча отбрасываются). При одном операторе
  поведение не меняется. Ограничение документировано.
− Терминал машины — один на сеанс (первый занявший), осознанная граница v1.
− Adaptive-bitrate в машинном мосту — статический потолок TOP_BITRATE на senders
  (JPEG-битрейт хелпера редко превышает); полноценный per-viewer adaptive машины —
  отдельное решение владельца на будущую волну.
