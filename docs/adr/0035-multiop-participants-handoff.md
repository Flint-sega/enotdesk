# 0035. Мультиоператор, этапы 2–3: список участников, передача управления, «только смотреть»

Дата: 2026-10-21. Статус: принято, выполнено (ветка `feature/multiop-2-3`). Наследует: 0030 (арбитраж ввода, видеослоты), 0032 (join к машине по паролю claim), 0033 (одна программа оператора).

## Контекст
С волны C (ADR 0030) в сеансе может быть несколько операторов: ввод у одного, остальные смотрят; кнопки «Взять/Отдать управление». Но оператор не видел, кто ещё в сеансе и у кого управление, а «Отдать» только освобождало ввод — коллеге приходилось самому нажимать «Взять». Старший специалист, который хочет только наблюдать, рисковал случайно получить управление: одинокий в сеансе или пришедший после «Отдать» получает ввод автоматически.

Владелец (21.10) поручил этапы 2–3 решить самому, по самому надёжному варианту.

## Решение
1. **Арбитр** (`client/lib/input-arbiter.mjs`, общий для attended-хоста и агента машины) получает:
   - `pass(from, to)` — активный передаёт ввод конкретному участнику, который в сеансе и не в режиме «только смотреть»; от не-активного — игнор;
   - `setViewOnly(op, on)` — «только смотреть»: такой участник не получает ввод ни автоматически, ни по `claim`, ни по `pass`, его события отбрасываются ДО инъекции; включение снимает ввод, если он был у него; выключение возвращает ввод, только если управлять больше некому (правило «одинокий получает ввод» из 0030);
   - `participants()` — `[{op, control, viewOnly}]`; `onChange` получает этот список третьим аргументом.
2. **Протокол** — тот же input-DataChannel, без изменений сервера и `/signal`:
   - оператор → хост: `{"type":"pass-input","to":"<claimId>"}`, `{"type":"view-only","on":true|false}` (рядом с `claim-input`/`release-input`); разбор — `parseControlMessage`, битое служебное в инъекцию не идёт;
   - хост → каждому оператору при каждом изменении и при открытии канала: `{"type":"participants","you":"<его claimId>","list":[{"id","name","control","viewOnly"}]}` (`participantsMessage`). Имена ставит хост из `operator-joined` — оператор не может переименовать других.
3. **Панель оператора** (`web/operator.*`): карточка «Участники» (скрыта, пока хост не прислал список), строки «имя (вы) — управляет/смотрит/только смотрит», кнопка «Передать управление» у того, кто сейчас управляет, галочка «Только смотреть». Тексты — словари ru/en, имена — `textContent`.
4. **Совместимость:** старые операторы игнорируют сообщение `participants` (у них по-прежнему кнопки 0030); старые хосты игнорируют `pass-input`/`view-only`, не шлют список — карточка не появляется. Сервер не меняется.

## Почему так
- «Только смотреть» — режим участника, а не роль на сервере: серверная роль наблюдателя (аудитор в сеансе) потребовала бы новой модели прав claim/join и миграции; здесь нужна защита от случайного захвата, а не граница прав. Это записано честно: оператор сам снимает режим.
- Передача — от активного без подтверждения получателем: получатель уже в сеансе и видит экран; подтверждение добавило бы шаг, а ошибочную передачу исправляет кнопка «Взять/Отдать».
- Список шлёт хост, а не сервер: состояние управления живёт на хосте (конвенция «решение о вводе — только host-сторона», 0030); сервер его не знает.

## Последствия
+ Каждый оператор видит состав сеанса и у кого управление; передача — в один клик; наблюдатель не может получить ввод случайно.
+ Работает в обоих типах сеанса (attended и машина) одним кодом арбитра; сервер не меняется.
− «Только смотреть» не защищает от злонамеренного оператора — он снимет галочку. Граница прав по-прежнему — роль и claim на сервере.
− Список ограничен 16 строками в панели (cap видеослотов 3, join без видео — участники чата).

## Проверка
Автотесты: арбитр (pass, view-only, список, разбор служебных), контракт панели (разметка, живые обработчики, ключи словарей), контракт host-рендерера. Живьём на Linux-ВМ лабы два оператора на одной машине: список у обоих с «вы», передача управления, «только смотреть» снимает ввод и игнорирует попытку взять управление, выключение режима при двух участниках ввод не выдаёт (MANUAL-QA, 21.10).
