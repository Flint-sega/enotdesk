# ADR 0014: чат, буфер обмена и файлы — поверх DataChannel сессии, релей сервера не расширяется

## Контекст

После установки видеосвязи сессии поддержки не хватало базовых инструментов общения: чата, передачи текста в буфере обмена и файлов. Серверный WS-релей по контракту (interfaces.md, frozen) передаёт только offer/answer/ICE — расширять его значило бы увеличить нагрузку и поверхность сервера.

## Решение

Все сессионные сервисы идут поверх уже установленных RTCPeerConnection — отдельными DataChannel с фиксированными именами (allowlist): `input` (ввод, существующий), `chat` (текст ≤2000 символов), `clip` (текст буфера ≤100 000 символов), `file` (файлы ≤200 МБ, чанки 64 КиБ, meta/accept/reject/done — JSON, полезная нагрузка — бинарные чанки того же канала). Логика протоколов — чистые модули `client/lib/{chat,clipboard-sync,file-transfer}.mjs`, покрытые тестами; рендерер только проводка и UI.

Приватность: синхронизация буфера у клиента выключена по умолчанию, включается галочкой; файл от оператора клиент принимает только явным «Принять» (клиент — непрофессиональный пользователь, молчаливое сохранение недопустимо); файл от клиента оператор принимает сам. Имена файлов сводятся к basename (пути и управляющие символы вырезаются), приёмник проверяет размер построчно — перелив отклоняется. Backpressure отправителя — через `bufferedAmount`/`bufferedamountlow`.

Видео-UX той же волной: полноэкранный режим, переключение «вписать/заполнить» (object-fit), потолок качества исходящего видео 2,5 Мбит/с (`RTCRtpSender.setParameters`), смена экрана/окна на ходу через `replaceTrack` без ренегоциации.

## Почему

Расширять серверный релей — отвергнуто: канал P2P уже зашифрован (DTLS), сервер не должен видеть и хранить содержимое сессии. Один мультиплексный JSON-канал — отвергнуто: смешение бинарных чанков и управления усложняет разбор; отдельные каналы дают естественный backpressure для файлов. Автоматическое сохранение файлов клиентом — отвергнуто по той же причине, что и включённый по умолчанию буфер: клиент не должен молча что-то принимать.

## Последствия

Чат и файлы существуют только внутри сеанса и не сохраняются на сервере — история переписки исчезает с закрытием (осознанное решение для приватности). Имена DC-каналов — часть контракта клиента; сервер их не видит и не валидирует. Лимиты (2000 символов / 100 КиБ / 200 МБ) зашиты в модули и тестируются; изменение лимитов — правка констант, совместимая на проводе благодаря валидации на приёмнике.

## Addendum (25.10.2026): буфер у клиента включён; файл от оператора — только после «Принять»

Сверено с кодом при автопрогоне A-4 (чат, буфер и файл 50 МБ в обе стороны на стенде).

- **Буфер у клиента включён по умолчанию** с волны v0.4.0 (галочка «Синхронизировать буфер обмена» стоит
  сразу, `state.clip.client = true`). Текст выше («выключена по умолчанию») описывает решение до v0.4.0.
  От клиента к оператору уходит только то, что клиент сам скопировал в окне EnotDesk (событие `copy`
  этого окна), а не любой буфер системы. От оператора к клиенту текст ложится в системный буфер.
- **Файл от оператора.** До 25.10 отправитель слал `file-meta`, сразу за ним куски и `file-done`, ответа
  `file-accept` не ждал. Клиент копил куски в памяти (до 200 МБ) с момента `file-meta`, а «Принять» только
  убирало кнопки: ссылка «Сохранить» появлялась и без нажатия. На диск файл попадал только по действию
  клиента (ссылка → «Сохранить как»), молча ничего не сохранялось.
- **Решение владельца 25.10: файл от оператора передаётся только после «Принять».** Оператор (`/operator`
  и окно оператора в приложении) шлёт `file-meta` и ждёт `file-accept` с тем же id; `file-reject` или новый
  файл снимают ожидание (`createAcceptGate` в `client/lib/file-transfer.mjs`). Клиент до «Принять» кусков не
  берёт (`createFileReceiver(meta, { requireAccept: true })`). Старая вкладка оператора, которая шлёт куски
  сразу, получит у клиента «передача прервана». Агент машины принимает сам и отвечает `file-accept` сразу,
  поэтому в сеансе с машиной ничего не меняется. Файл от клиента оператор по-прежнему принимает сам.
  Порядок совпадает с таблицей протокола в [SESSION_PROTOCOL.md](../SESSION_PROTOCOL.md):
  `meta → accept/reject → куски → done`. Сторона оператора приходит с обновлением сервера (страницу
  `/operator` отдаёт сервер), сторона клиента — с выпуском приложения; клиенты 0.6.29 и раньше шлют
  `file-accept` по нажатию, так что новый оператор с ними работает.
