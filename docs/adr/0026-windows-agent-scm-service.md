# ADR 0026: Windows-служба агента — родительский SCM-режим на koffi (EDESK_AGENT_SVC=1)

Дата: 2026-09-28. Статус: принято. Контекст: приёмка 28.09, W-U2 — `sc start EnotDeskAgent`
падал 1053 (Event 7009/7000): Electron-exe не вызывал `StartServiceCtrlDispatcher`, SCM убивал
процесс по стартовому таймауту 30 с; failure-actions на это не реагируют (стартовый таймаут —
не «сбой»).

## Решение

Один и тот же exe несёт три режима. При `EDESK_AGENT_SVC=1` (ставится в AppEnvironment службы
вместе с `EDESK_AGENT=1`) процесс **не инициализирует Electron**: ветка стоит до первого
обращения к `app`, импорт `win-service.mjs` динамический. Процесс становится тонким SCM-родителем:

- `StartServiceCtrlDispatcherA` вызывается **асинхронно** (koffi `.async`) — блокируется поток
  libuv, главный JS-поток свободен;
- колбэки `ServiceMain` и обработчик управления регистрируются через `koffi.register`; по доке
  koffi вызовы из чужих потоков встают в очередь главного JS-потока — отдельной синхронизации
  не нужно;
- `ServiceMain`: `RegisterServiceCtrlHandlerExA` → START_PENDING → spawn ребёнка (тот же exe,
  `EDESK_AGENT=1`, без `EDESK_AGENT_SVC`) → RUNNING;
- STOP/SHUTDOWN: STOP_PENDING → `taskkill /T /F` дерева ребёнка → STOPPED;
- падение ребёнка: рестарт с эскалацией 1/2/5/10 с, кап 30 с, сброс счётчика после 60 с
  стабильной работы; после 5 падений подряд — честный SERVICE_STOPPED, службу рестартуют
  SCM-failure actions (5с/10с/30с) целиком.

Переменные службы ставятся в `Environment` под ключом службы — его читает сам services.exe;
`AppEnvironment` services.exe НЕ читает (конвенция обёрток srvany/nssm — прежняя документация
репозитория ошибалась, найдено ревью 28.09), install-скрипт пишет оба значения для совместимости.

Логика жизненного цикла отделена от koffi-клея (`createScmParentLogic`) и покрыта тестами на
инъекциях без koffi/Windows (`client/test/win-service.test.mjs`).

## Рассмотрённые альтернативы

- **Task Scheduler-задача от SYSTEM** — без нового кода, но служба исчезает из `services.msc`,
  семантика управления меняется, W-U2/U4 пришлось бы переписывать.
- **Свой нативный srvany/exe-обёртка** — второй бинарник в сборке и в подписи/дистрибуции.
- **Отложить на v0.5** — unattended-Windows остаётся нерабочим, а это приоритетная фаза приёмки.

## Следствия

- Плюс: настоящая служба в `services.msc`, `sc`-управление, чек-лист W-U2/U3/U4 выполняется как
  написан; никакой второй зависимости (koffi уже в рантайме).
- Минус/риск: SCM-родитель живёт в том же asar — размер служебного процесса ≈ Electron; Node
  child_process + koffi-колбэки в служебном процессе — новая поверхность, покрытая тестами
  логики; живое поведение службы проверяется MANUAL-QA (автотесты SCM не вызывают).
- Нюанс: пути к exe у per-machine установки (Program Files) и у существующих per-user установок
  различаются — install-скрипт требует явного APP_EXE.
