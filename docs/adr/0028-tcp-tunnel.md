# ADR 0028: TCP-туннель в machine-сеансе — DC-канал `tunnel` на allowlist целей; операторская сторона сознательно отложена

## Контекст

Поддержке регулярно нужен доступ к сервисам самой машины — RDP (`127.0.0.1:3389`), SSH (`127.0.0.1:22`) — без проброса портов наружу и без VPN. Прецедент есть: терминал (ADR 0021) — DataChannel-канал поверх утверждённого machine-сеанса, та же политика причины/PIN, проверенных сервером; релей сервера по ADR 0014 не расширяется (только offer/answer/ICE). v0.6 — каркас: модуль `client/lib/tunnel.mjs` + ADR + юнит-тесты, без UI и без подключения в диспетчер каналов (другой исполнитель, включение — следующий цикл).

## Решение

Туннель — DC-канал `tunnel` в machine-сеансе, открытие только внутри утверждённого сеанса (pc живёт после approved — как у `term`). Агентская сторона `createTunnelHost`: канал ждёт control-кадр `{type:'open', target:'host:port'}`; target валидируется **строго по allowlist** — по умолчанию только loopback: `127.0.0.1:3389` и `127.0.0.1:22`; список задаётся на машине env `ENOT_TUNNEL_ALLOWLIST` (элемент `host:port` фиксирует порт, `host` — любой валидный порт на этом хосте), произвольные хосты запрещены всегда. Отказ — честный кадр `{type:'error', code:'target_not_allowed'}`, канал остаётся открытым для исправления target. Успех → `net.connect` (в тестах — инъекция `netFactory`, шов по образцу фейк-PTY терминала) → двунаправленный насос: бинарные чанки DC ↔ данные сокета; control-кадры `opened`/`error`/`close` — тот же сплит «JSON-строки = control, бинарные = данные», что в file-transfer/machine-services (ADR 0014). Socket close/error → честный кадр и `ch.close()`; закрытие DC → `socket.destroy()`. Лимиты: 1 активный туннель на канал (второй `open` — `tunnel_busy`, по образцу term-busy) и потолок туннелей на host-сторону (1 по умолчанию, как 1 терминал на машину); открытие/закрытие — в аудит (`tunnel.open`/`tunnel.close` через переходы heartbeat агента, как `term.open`/`term.close`).

**Операторская сторона сознательно отложена.** Потребителя туннеля в v0.6 нет: браузер не умеет слушать TCP-порты, а два пути к потребителю расходятся — (а) desktop-оператор с machine-сеансами (ещё не существует) или (б) серверный TCP-релей, который ломает ADR 0014 («релей не расширяется») и потому отвергается. Оба варианта зафиксированы как открытый вопрос следующего цикла; каркас открывает туннель, но в реальном сценарии данных через него не пойдёт — это заявленная граница v0.6, не готовая фича.

## Почему

Allowlist — единственная оборона от превращения машины в открытый прокси: агент-служба работает от SYSTEM (ADR 0021) и имеет сетевые права хоста; без жёсткого списка любой утверждённый оператор смог бы сканировать внутреннюю сеть клиента и ходить в произвольные сервисы. Loopback по умолчанию закрывает главный сценарий (локальные RDP/SSH) и не тянет наружу; расширение списка — осознанное действие администратора машины, а не умолчание. Отказ allowlist не закрывает канал — оператору дешевле исправить target, чем пересоздавать DataChannel (ренеготиация). Инъекция `netFactory` и фейковые сокеты — единственный новый тестовый шов: реальные TCP-соединения не тестируются автоматически (MANUAL-QA). Отвергнуто: белый список на стороне сервера (туннель не проходит через сервер — проверять нечего) и разрешение произвольных хостов за флагом (та же дыра, что отсутствие allowlist).

## Последствия

Backpressure socket→DC на каркасном уровне не реализован: мост агента (ADR 0021) сам держит очередь ≤1 МБ и роняет переполнение — для TCP-стрима это повреждение потока, приемлемое только пока потребителя нет; настоящий backpressure (pause/resume сокета по `bufferedAmount`, по образцу file-transfer) — обязательный пункт операторского цикла. IPv6 (скобочная нотация) парсером не поддержан — только `host:port` IPv4/hostname; расширение не ломает протокол. Чанк больше 256 КБ трактуется как порча протокола — туннель честно рвётся кадром ошибки (`chunk_too_large`), а не молча теряет байты. `ENOT_TUNNEL_ALLOWLIST` парсится агентом/диспетчером следующего цикла — модуль принимает уже разобранный список, мусорный env обязан давать дефолт loopback, а не пустой allowlist. Аудит и аудит-события — в агентской части следующего цикла (сам модуль аудита не пишет). Операторская сторона — открытым вопросом: выбор между desktop-оператором с machine-сеансами и отказом от TCP-релея должен получить собственное решение до включения UI.
