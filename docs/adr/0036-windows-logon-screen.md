# 0036. Экран входа и блокировки Windows: хелпер от SYSTEM в консольном сеансе

Дата: 2026-10-21. Статус: принято, реализовано в ветке `feature/win-logon-screen`; результат живой проверки — в разделе «Проверка». Наследует: 0026 (служба = SCM-родитель), 0027 (хелпер в консольном сеансе, DXGI/GDI, named pipe), 0006 (attended-клиент по-прежнему не трогает экран входа).

## Контекст
Хелпер видео и ввода unattended-машины запускался токеном вошедшего пользователя (`WTSQueryUserToken` → `CreateProcessAsUserW`). Отсюда три ограничения, которые ADR 0027 записал как известные:
- **экран блокировки и UAC.** Рабочий стол Winlogon недоступен процессу пользователя: DXGI-дубликат теряется (`ACCESS_LOST`), пересоздать его на Winlogon нельзя, при частых потерях хелпер честно выходит;
- **никто не вошёл (экран входа после перезагрузки).** `WTSQueryUserToken` не возвращает токена, и хелпер не стартует вообще;
- **ввод на защищённом столе.** Ввод от процесса пользователя туда не проходит.

AnyDesk, TeamViewer и RustDesk решают это одинаково: служба запускает свой процесс от SYSTEM внутри консольного сеанса, и процесс следует за текущим рабочим столом ввода.

## Решение
1. **Токен SYSTEM в консольном сеансе** (`client/lib/session-spawn.mjs`, `tokenMode: 'system'`). Служба (LocalSystem) открывает свой токен, дублирует его в primary (`DuplicateTokenEx`) и записывает номер консольного сеанса (`SetTokenInformation(TokenSessionId)`, нужен SeTcbPrivilege, у LocalSystem он есть). Затем `CreateProcessAsUserW` с `winsta0\default`.
   - При любом сбое — честный откат на токен пользователя (лог `session-spawn: … откат`).
   - Аварийный выключатель: `ENOT_VIDEO_TOKEN=user` в окружении службы.
   - **Только из защищённой папки** (security-review 21.10, `helperLaunchPlan`): от SYSTEM хелпер запускается лишь из `Program Files` (установка NSIS, ADR 0029), без копии в ProgramData. В папке распаковки портативки (`C:\Windows\TEMP\<имя сборки>\resources`) и в `ProgramData\EnotDesk\helper` у Users есть права создавать файлы (`WD,AD`, проверено на ВМ лабы), а Windows грузит несистемные DLL (например `dxgi.dll`) из папки программы раньше системных — подложенная DLL исполнилась бы от SYSTEM. Вне Program Files остаётся прежний путь: токен пользователя и копия в ProgramData (роста прав нет). Служба в продукте ставится только установщиком (ADR 0029); портативка в роли службы бывает лишь в лабе.
2. **Захват следует за рабочим столом** (хелпер). Перед каждым созданием DXGI-дубликата поток захвата прицепляется к текущему рабочему столу ввода (`OpenInputDesktop` + `SetThreadDesktop`).
   - После блокировки или UAC дубликат пересоздаётся уже на Winlogon. Процессу от SYSTEM это разрешено; процессу пользователя — нет, у него прежнее поведение.
   - Лог `{"ev":"capture-desktop","attach":"ok|failed","desktop":…}` пишется только при смене исхода.
   - Выключатель: `ENOT_VIDEO_FOLLOW=off`.
3. **Ввод** использует существующий механизм перепривязки потока ввода к рабочему столу ввода (D3, ADR 0027 addendum). Ему нужна стратегия attach. На ВМ лабы с `ENOT_VIDEO_ATTACH=off` (обход X4) ввод на экране блокировки невозможен по построению; это записано как граница.
4. **Стартовый кадр** (найдено в лабе 21.10). На статичном экране DXGI не отдаёт ни одного кадра, особенно сразу после пересоздания дубликата на новом рабочем столе. Если за 1,5 с кадров нет, один снимок GDI уходит как стартовый. Выключатель: `ENOT_VIDEO_SEED=off`.

5. **Журналы и журнал безопасности** (ревью безопасности 22.10, P2-5 и P2-8).
   - `%ProgramData%\EnotDesk` служба на старте закрывает (`client/lib/programdata-acl.mjs`): владелец — SYSTEM, доступ — SYSTEM и Администраторы, Пользователи видят только саму папку и `helper\` (копия хелпера для токена пользователя). Подменённая заранее папка-ссылка отодвигается, ссылки внутри удаляются. Хелпер и svc-diag перед каждой записью сами проверяют, что ни папка, ни файл журнала не ссылка (`win.rs` `open_journal`, `isPlainFile`): сбой прав значит «нет файлового журнала», а не запись SYSTEM в чужой файл.
   - Экран входа и блокировки и окно UAC — в журнале сервера: хелпер сообщает состояние стола (`locked`, `uac`), агент считает нажатия, клики и прокрутку на нём и передаёт heartbeat'ом (`secureDesktop`, `secureInputs`). Сервер пишет `security.desktop.enter`, первый ввод за период `security.input`, `security.desktop.leave` с числом действий. Записи `security.*` не отключаются выключателем журнала (ADR 0034).

## Почему так
- SYSTEM — единственный штатный способ увидеть Winlogon и работать без вошедшего пользователя. Отдельный «логон-хелпер», который служба перезапускает при смене стола, добавил бы гонки при каждой блокировке и разблокировке. Один SYSTEM-хелпер, следующий за столом, проще и совпадает с практикой отрасли.
- Права хелпера от этого не растут для оператора: хелпер умеет только захват и инъекцию ввода по аутентифицированному pipe (DACL: SYSTEM и администраторы, одноразовый токен hello). Терминал агента и так работает от SYSTEM (R09).
- Откат на токен пользователя и выключатели сохраняют прежнее поведение, если на какой-то машине SYSTEM-путь поведёт себя хуже.

## Последствия
+ Unattended-машина видна оператору на экране блокировки и, если ввод разрешён стратегией attach, управляема на нём. После перезагрузки без входа пользователя хелпер стартует.
+ Статичный экран больше не даёт оператору «чёрное до первого движения».
− Хелпер работает от SYSTEM в сеансе пользователя: ошибка в хелпере дороже. Смягчение — тот же узкий протокол и pipe-DACL, что и раньше.
− На машинах, где нужен `ENOT_VIDEO_ATTACH=off` (X4), ввод на экране блокировки недоступен.
− Attended-клиент (ADR 0006) экран входа по-прежнему не видит. Это осознанная граница: доступ живёт только пока окно клиента открыто.

## Проверка
Автотесты: путь SYSTEM-токена и откат (session-spawn). Живая проверка на ВМ лабы — см. MANUAL-QA, запись 21.10 «экран входа/блокировки».
