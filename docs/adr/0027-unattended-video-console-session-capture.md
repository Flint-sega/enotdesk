# ADR 0027 (draft): Unattended-видео — хелпер в консольном сеансе + DXGI, транспорт решается замером

## Статус

Спайк ВЫПОЛНЕН 01.10 (машина приёмки, код `spike/video-dxgi/`), механика
подтверждена. Решение: строим v0.5 на хелпере с DXGI + WIC JPEG; транспорт —
кадры через службу в существующий WebRTC-стек (вариант «а»). Полная реализация
— следующий этап v0.5 (хелпер-процесс, IPC, мост, приватность).

## Контекст

Сравнение с RustDesk 1.4.8 / TeamViewer Remote 15 / AnyDesk 9.6 (01.10) показало:
единственный серьёзный функциональный разрыв — **unattended-видео**. Наш агент —
Electron-процесс в session 0: `getDisplayMedia` там не видит консольный рабочий
стол (session isolation Windows). Все трое конкурентов решают это перехватом
консольной сессии службой. Без этого мы ограничены сценарием «позвони — помогу».

Ограничения v1 (ADR 0001, MANUAL-QA W-U7) признавали это осознанным пределом;
решение о закрытии разрыва принято после живой приёмки v0.4.6–v0.4.8.

## Решения (опрос владельца 01.10)

1. **Порядок v0.5+:** видео-спайк первым; чат/файлы в machine-сеансах (W-U6),
   WoL, TCP-туннель — параллельными малыми волнами; стабилизация — по остатку.
2. **Целевой юзер:** сначала «сам себе хостер» (энтузиасты/малый бизнес), далее
   внутренний IT (SSO/LDAP, политики), затем MSP/white-label.
3. **Механизм session 0:** **хелпер-процесс внутри активного консольного сеанса**
   (служба запускает его токеном сеанса) + **DXGI Desktop Duplication**
   (60 FPS, аппаратный курсор). Спайк проверяет: локскрин, UAC secure desktop,
   два монитора, отключённая мышь/клавиатура.
4. **Транспорт кадров:** в спайке замеряются ОБА варианта на одной машине —
   (а) сырые кадры → служба (shared memory) → существующий WebRTC-мост
   (CPU-кодирование, быстрое переиспользование операторского стека);
   (б) хелпер кодирует сам (NVENC/QuickSync) и шлёт RTP напрямую.
   Решение — по цифрам FPS/CPU/латентности, не по ощущениям.
5. **Отклонённые пути:** GDI/BitBlt из службы (низкий FPS, нет UAC/локскрина);
   RDP-shadow (тянет RDP-стек + групповые политики); IddCx драйвер (отдельный
   проект с подписью WHQL).

## План спайка (2–3 дня)

- Windows-машина приёмки (DESKTOP-SG8OSGN, Win10 19045, бот-админ доступен).
- Хелпер: минимальный C++/Win32 — запуск в сеансе юзера, DXGI-дублирование
  первичного монитора, кадры в shared memory + счётчики FPS/CPU.
- Транспорт-а: читатель в Node (службе) → скрытый мост → WebRTC оператору
  (существующий стек, терминальная схема ADR 0021).
- Транспорт-б: хелпер → RTP в тот же операторский peer (libdatachannel).
- Замеры: FPS, CPU хелпера и службы, латентность «движение→кадр у оператора»,
  поведение на локскрине/UAC.

## Критерии выхода из спайка

- Локскрин и UAC видны (или честно задокументировано «не видно, причина X»).
- ≥24 FPS на 1600×900 при CPU хелпера ≤15% одного ядра хотя бы на одном
  транспорте.
- Кадры доходят до существующего веб-оператора без изменений протокола
  (транспорт-а) — либо задокументирована цена доработки (транспорт-б).

## Последствия

- При успехе: v0.5 строит на выбранном транспорте полный unattended-сеанс
  (видео + input-пайплайн в сеансе юзера + privacy mode как следствие
  захвата). Служба и хелпер — новые нативные компоненты (подпись, обновление).
- При провале обоих транспортов по цифрам — вернуться к владельцу с фактами
  и вопросом «IddCx-драйвер или отложить».

## Результаты спайка (01.10, DESKTOP-SG8OSGN, Win10 19045, GTX 1050 Ti)

Метод: Rust-бенчмарк `spike/video-dxgi/` (windows-rs 0.58, чистый Win32,
без зависимостей от монорепо RustDesk). Механика RustDesk подтверждена по их
исходникам: служба (SYSTEM) запускает `--server` процесс В КОНСОЛЬНОМ СЕАНСЕ
через токен winlogon (`launch_privileged_process`, src/platform/windows.rs:832);
захват делает пользовательский процесс. Их capture-библиотека `scrap` —
монорепо-зависимость (hbb_common/base/bindgen) — в спайк не бралась.

Числа (вариант спайка, DXGI Desktop Duplication + WIC JPEG):

- DuplicateOutput на 1600×900 создаётся мгновенно; захват+map кадра
  **3.07 мс** (≈320 FPS мощности захвата) — критерий «≥24 FPS» перекрыт с
  запасом ×13.
- JPEG (WIC, native 1600×900): **14.9 мс, 169 КБ/кадр**; конвейер
  «захват+JPEG» ≈ 18 мс/кадр ⇒ ≈55 FPS ёмкости, на 24 FPS ≈ 45% ядра —
  в проде снижается downscale до 720p и/или turbojpeg; static-десктоп кадров
  не производит вообще (CPU → 0), что и требуется.
- Контрольный GDI-вариант (BitBlt+CAPTUREBLT, 1280×720, q75): захват 23.4 мс
  (в 8 раз хуже DXGI), устойчиво 18.75 FPS при 63% CPU — GDI-путь отвергнут
  цифрами (совпадает с «отклонёнными путями» выше).
- Локскрин/UAC в спайке не замерялись (машина без присмотра, будить нечем);
  остаётся в приёмке реализации — ожидаемо работает, т.к. дубликация идёт
  с уровня DWM-композиции, а не с GDI-экрана.

**Ключевая находка эксплуатации: при погасшем дисплее (DPMS) дубликация
создаётся, но AcquireNextFrame вечно DXGI_ERROR_WAIT_TIMEOUT — ноль кадров
даже при движении курсора через SetCursorPos (это не «настоящий» ввод).
Пробуждение дисплея возвращает кадры мгновенно (PROBE OK за 1 мс). Отсюда
продуктовое требование: при claim machine-сеанса служба обязана разбудить
дисплей (SC_MONITORPOWER/SendInput), и это же — фундамент будущего
privacy mode (наоборот: гасить дисплей при активном управлении).**

Критерии выхода: захват ✔ (запас ×13), JPEG ✔ (умещается с даунскейлом),
«кадры до существующего веб-оператора без изменений протокола» — на стадии
реализации (транспорт-а: кадры → служба → скрытый мост → canvas.captureStream;
протокол сигналинга не меняется). Спайк считается успешным; цена провала
транспорта-а снята с повестки.

## Addendum 07.10.2026: GDI-fallback захвата

### Решение

GDI/BitBlt как ОСНОВНОЙ путь остаётся отвергнутым — цифры спайка не изменились
(23.4 мс/кадр, 18.75 FPS при 63% ядра против ~3 мс и ×13 запаса у DDA).
Принят как FALLBACK: хелпер стартует в DXGI-режиме и **один раз за жизнь
процесса** может переключиться на GDI/BitBlt (CreateDIBSection top-down BGRA,
BitBlt SRCCOPY|CAPTUREBLT, первичный монитор; контракт grab/size/buf идентичен
DXGI-пути — downscale, WIC-энкодер и протокол пайпа не меняются). После
переключения DXGI не ретраится до конца процесса.

### Триггеры переключения

- **(а) `dup-fail`:** ≥5 подряд отказов make_dup, суммарно ≥5 с от первого
  отказа серии, И процесс ни разу не доставил кадр (`ever_framed`). Машина,
  где DDA уже доставлял кадры, сохраняет прежнюю лестницу: 50 подряд отказов
  (~10 с) → exit 2 — UAC/локскрин на здоровой машине никогда не деградирует
  захват.
- **(б-v2) `black-frames`:** 10 подряд доставленных DDA-кадров, сплошно
  чёрных (каждый 16-й выборочный пиксель имеет max(R,G,B) ≤ 8/255), при
  выключенном privacy-sleep. Нулевой (static) десктоп — НОРМА и никогда не
  переключает режим.
- **(в) `no-dxgi`:** D3D11/DXGI-стек не создался вовсе при старте → GDI с
  собственным WIC-фабрикой; не вышло — честный exit 1 как раньше.

Первоначальный вариант (б) «ноль кадров → переключение» был ОТКЛОНЁН до
релиза: ноль кадров — норма и для здорового idle-десктопа (см. результаты
спайка выше: «static-десктоп кадров не производит вообще, CPU → 0»), такой
триггер ложно срабатывал бы через ~15–20 с каждого простаивающего сеанса и
ломал CPU-экономику, ради которой делался спайк. Пока privacy_sleep активен,
переключение запрещено и в GDI-режиме захват не ведётся: остаток фреймбуфера
погасшего дисплея не должен утекать оператору.

### Факты живого прогона (07.10, VM 101 enotdesk-win10-a1, Microsoft Basic Display Adapter)

Метод: standalone-хелпер в консольном сеансе (`schtasks /IT`), PS-клиент пайпа
(`scripts/lab/gdi-test.ps1` + `scripts/lab/gdi-run.cmd`); детали и артефакты —
MANUAL-QA, раздел 07.10.2026.

- Прогон 1 (rev-1, 45 с): DDA создаётся и отдаёт 34 кадра (~0.75 fps); статусы
  повторяют `{"mode":"dxgi","fps":0..2,"lastErr":"capture: long timeout,
  display wake attempted"}`; сохранённый кадр №1 — сплошной чёрный
  (попиксельно: mean 0.000, max 0).
- Прогон 3 (rev-2, 60 с, dump всех кадров): 43 кадра; попиксельный анализ:
  42/43 — РЕАЛЬНОЕ содержимое рабочего стола ВМ (средняя люма ~57.8, max 255;
  визуально: taskbar, часы 1:17 07.10.2026, cmd-окно, окно агента EnotDesk);
  чёрный только кадр №1. Каждый wake (~раз в 5 с) выдавливает из композиции
  1–2 кадра — отсюда слайдшоу.
- **Ключевое ИСПРАВЛЕНИЕ вывода от 06.10:** DDA на Microsoft Basic Display
  Adapter НЕ «невозможна в принципе» — она работает и доставляет реальный
  рабочий стол, но как слайдшоу ~0.7 fps. Fallback на этом стенде корректно НЕ
  срабатывает (DDA доставляет не-чёрное содержимое) — валидация «нет ложного
  срабатывания». Истинный positive-кейс (мёртвый или перманентно чёрный DDA)
  на стенде недоступен; живая валидация fallback = прогон G-3 + два раунда
  ревью GLM-5.3-Flash (оба CONFIRMED; закрыты: ever_framed-гейт против no-op
  wake на Modern Standby, 5-секундный временной guard против UAC/локскрина,
  замена zero-frames-триггера на black-frames).
- Остаточный риск (из ревью, задокументирован): полноэкранный чисто-чёрный
  анимированный скринсейвер на здоровой DDA-машине benign-переключит на GDI —
  тот же чёрный контент, цена только CPU.
- Открытый вопрос (ROADMAP): slideshow-DDA ~0.7 fps — low-fps-триггер нельзя
  безопасно отличить от здорового idle-DDA без input-probe («доходит ли
  синтетический ввод хелпера до экрана?»); тот же вопрос, что W-U7.

### Addendum 2 (07.10.2026 вечер, rev-3b / 0.6.7-pre.3): ввод — SendInput отклоняется с Access Denied; позиционирование мыши переведено на SetCursorPos

Факты X-серии-2 (полные таблицы — MANUAL-QA, раздел «X-серия-2»):

- На ВМ 101 (Microsoft Basic Display Adapter) **SendInput отклоняется системой
  с ERROR_ACCESS_DENIED (5) для всех событий** — мышь absolute/relative И
  клавиатура; устаревший `mouse_event` тоже не действует. Отказ не зависит от:
  контекста спавна (сервис/standalone), IL вызывающего (Medium/High),
  состояния дисплея (VIDEOIDLE 600 c → 0 + wake-бродкаст), прав десктопа
  потока (attach ok с WRITEOBJECTS, `tray=yes`). `SetCursorPos` на том же
  потоке работает в обоих контекстах. Точная механика блока — открытый вопрос:
  хелпер с attach получает возврат 0 + Access Denied, PS-прогон без attach —
  возврат 1 с тихим проглатыванием события; поведение «плавает» во времени.
- **Продуктовое решение**: абсолютное позиционирование мыши
  (`buttons:"move"`) выполняется через `SetCursorPos` в пикселях виртуального
  стола; кнопки/колесо/клава остаются на SendInput (фолбэка для них нет — на
  ВМ этого класса они остаются неработающими, что честно видно в телеметрии
  `lastErr` с текстом gle; решение по кликам/клаве — за владельцем). Отказ
  инъекции теперь несёт `GetLastError` + текст через `FormatMessageW`
  (`gle=5 (Access is denied.)` в `lastErr`/трассе; оговорка: SendInput не
  обязан ставить LastError, `0 (not set)` — валидное наблюдение).
- **Живая приёмка сквозного продуктового пути** (Edge на ВМ 102 → /operator →
  машинный сеанс pre.3 → смахивание 44 точек по видео): курсор ходит по всему
  экрану, телеметрия видео «0% потерь». Видео-конвейер pre.3 подтверждён этим
  же прогоном.
- Лабовая диагностика: команда `probe3` (полная матрица инъекции одним
  проходом) и автопробер `ENOT_VIDEO_AUTOPROBE_SECS` (теперь шлёт probe3) —
  только за env/ручной командой, продуктовых вызовов нет.

Калибровка D5 («input-dead-video»), состояние на момент addendum — жёсткий
гейт плана §3.2 соблюдён: **код триггера не пишется, пока пороги не
зафиксированы здесь**.

- VM-сторона (ВМ 101, слайдшоу-DDA, измерено): idle `pr=0, empty=0–2/2 c`;
  wake-кадры `pr 0–3/2 c`; probe-нуджи дают pointer-only acquisitions
  (`empty>0`) — сигнал L2/Q4 жив; верифицированный ввод (SetCursorPos-проба)
  работает в обоих контекстах → строительный блок «verified probes» доступен.
- Healthy-сторона (C2–C4 плана: `pr` при активном вводе на здоровой машине,
  «нуджа без present» Q3, pointer-метаданные Q4) — **не измерена**: требует
  реального ПК владельца; ВМ 102 не заменяет (тот же Basic Display Adapter).
- Черновик формулы (В-В плана, «верифицированный ввод без отклика захвата»):
  переключение при одновременном `mode=dxgi`; `ever_framed`; `!privacy`;
  `!uac`; `!locked`; одномониторная топология; `verified_probes ≥ 5` в окне
  20 с; порог по презентам — по ветке Q3 (ветка «нуджа даёт present»:
  `real_presents ≤ verified_probes/2`; ветка «не даёт»: абсолютный порог над
  слайдшоу-уровнем + обязательный сигнал L2). Константы **умышленно не
  фиксируются** до healthy-измерений — по одной ВМ порог зафиксировать нельзя.
- Выключатель поля: env `ENOT_VIDEO_UNRESPONSIVE=0` (реализация D9) отключает
  триггер целиком; one-shot необратим в рамках процесса.

## Addendum 3 (08.10, X4): стратегия attach — инъекция ввода на BDA-ВМ поднята без брокера

Контекст: после sess-диагностики (sess=1/1, «helper не в той консоли»
опровержён) владелец дал слово «делай X4, доведи до рабочего». Дешёвый
пробник P0v2 (schtasks-процесс в консольном сеансе, корректный INPUT cbSize=40)
показал: **базовый SendInput на этой ВМ работает** (`sent=1`, курсор реально
сдвигается) — мишенью стал не токен/спавн, а наш собственный attach.

Корень: постоянный `SetThreadDesktop(OpenInputDesktop(...))` на этой ВМ
превращает ВЕСЬ SendInput в честный `ERROR_ACCESS_DENIED` (gle=5), при том что
та же инъекция с потока на lpDesktop-десктопе проходит. На реальных машинах
зависимость обратная (приёмка 02.10: без attach инъекция молча глотается) —
поэтому решение за env, а не за сменой дефолта:

- **`ENOT_VIDEO_ATTACH=off`** — стратегия без attach (инъекция с
  lpDesktop-десктопа; ретрай-блок и D3-перепроверка не выполняются, в
  input-логе `"attach":"off"`);
- `on` / не задан — прежнее поведение (attach + ретраи + D3), дефолт не
  тронут; пересмотр дефолта — после калибровки C2–C4 (гейт D5).

Живое доказательство (ВМ 101, helper с флагом, листенер GetAsyncKeyState в
консольном сеансе): **6 из 6 кликов оператора зарегистрированы в заданных
точках, нажатие клавиши — зарегистрировано**; SetCursorPos-нуджи работают
(`attach:"off"`, `err:""` в тиках). Winlogon-брокер и второй процесс НЕ
понадобились — схема конкурентов (RustDesk/AnyDesk) на эту проблему легла, но
оказалась избыточной: у них брокер живёт в активном сеансе без нашего attach.

Открытое: почему SetThreadDesktop на этой ВМ ломает SendInput — не выяснено
(QEMU/virtio-vga-специфика; sess/десктопы/IL проверены корректными). Если
калибровка C2–C4 покажет, что healthy-машины инъецируют и без attach,
дефолт можно перевернуть на off+fallback и убрать флаг.
