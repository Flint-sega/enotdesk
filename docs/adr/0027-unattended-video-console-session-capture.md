# ADR 0027 (draft): Unattended-видео — хелпер в консольном сеансе + DXGI, транспорт решается замером

## Статус

Предложено (спайк не выполнен). Решения зафиксированы опросом владельца 01.10.

## Контекст

Сравнение с RustDesk 1.4.8 / TeamViewer Remote 15 / AnyDesk 9.6 (01.10) показало:
единственный серьёзный функциональный разрыв — **unattended-видео**. Наш агент —
Electron-процесс в session 0: `getDisplayMedia` там не видит консольный рабочий
стол (session isolation Windows). Все трое конкурентов решают это перехватом
консольной сессии службой. Без этого мы ограничены сценарием «позвони — помогу».

Ограничения v1 (ADR 0001, MANUAL-QA W-U7) признавали это осознанным пределом;
решение о закрытии разрыва принято после живой приёмки v0.4.6–v0.4.8.

## Решения (опрос владельца 01.10)

1. **Порядок v0.5+:** видео-спайк первым; чат/файлы в machine-сеансах (W-U6),
   WoL, TCP-туннель — параллельными малыми волнами; стабилизация — по остатку.
2. **Целевой юзер:** сначала «сам себе хостер» (энтузиасты/малый бизнес), далее
   внутренний IT (SSO/LDAP, политики), затем MSP/white-label.
3. **Механизм session 0:** **хелпер-процесс внутри активного консольного сеанса**
   (служба запускает его токеном сеанса) + **DXGI Desktop Duplication**
   (60 FPS, аппаратный курсор). Спайк проверяет: локскрин, UAC secure desktop,
   два монитора, отключённая мышь/клавиатура.
4. **Транспорт кадров:** в спайке замеряются ОБА варианта на одной машине —
   (а) сырые кадры → служба (shared memory) → существующий WebRTC-мост
   (CPU-кодирование, быстрое переиспользование операторского стека);
   (б) хелпер кодирует сам (NVENC/QuickSync) и шлёт RTP напрямую.
   Решение — по цифрам FPS/CPU/латентности, не по ощущениям.
5. **Отклонённые пути:** GDI/BitBlt из службы (низкий FPS, нет UAC/локскрина);
   RDP-shadow (тянет RDP-стек + групповые политики); IddCx драйвер (отдельный
   проект с подписью WHQL).

## План спайка (2–3 дня)

- Windows-машина приёмки (DESKTOP-SG8OSGN, Win10 19045, бот-админ доступен).
- Хелпер: минимальный C++/Win32 — запуск в сеансе юзера, DXGI-дублирование
  первичного монитора, кадры в shared memory + счётчики FPS/CPU.
- Транспорт-а: читатель в Node (службе) → скрытый мост → WebRTC оператору
  (существующий стек, терминальная схема ADR 0021).
- Транспорт-б: хелпер → RTP в тот же операторский peer (libdatachannel).
- Замеры: FPS, CPU хелпера и службы, латентность «движение→кадр у оператора»,
  поведение на локскрине/UAC.

## Критерии выхода из спайка

- Локскрин и UAC видны (или честно задокументировано «не видно, причина X»).
- ≥24 FPS на 1600×900 при CPU хелпера ≤15% одного ядра хотя бы на одном
  транспорте.
- Кадры доходят до существующего веб-оператора без изменений протокола
  (транспорт-а) — либо задокументирована цена доработки (транспорт-б).

## Последствия

- При успехе: v0.5 строит на выбранном транспорте полный unattended-сеанс
  (видео + input-пайплайн в сеансе юзера + privacy mode как следствие
  захвата). Служба и хелпер — новые нативные компоненты (подпись, обновление).
- При провале обоих транспортов по цифрам — вернуться к владельцу с фактами
  и вопросом «IddCx-драйвер или отложить».
