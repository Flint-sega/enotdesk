# EnotDesk Guest Pilot для Linux

Оба участника запускают одно приложение с адресом одного пилотного сервера. Владелец экрана нажимает «Получить помощь», копирует ссылку и отправляет её помощнику. Помощник открывает «Помочь», вставляет ссылку и отправляет запрос. Для доступа к экрану и управлению требуется подтверждение владельца. Он может остановить сеанс кнопкой завершения или закрытием приложения. Чтобы поменяться ролями, второй участник начинает новый сеанс и передаёт новую ссылку.

Ссылка действует пять минут, погашается при первом подключении и даёт доступ к одному сеансу. Для управления мышью и клавиатурой Linux-клиенту нужна сессия X11. При установленном TURN обе стороны используют WebRTC relay, а обмен сообщениями сигналинга идёт через WSS.

## Отдельный сервер

Из отдельного каталога с этой веткой, используя Node.js 24.12 или новее:

```sh
npm ci --omit=dev --ignore-scripts
npm run server
```

Порт по умолчанию — `127.0.0.1:17880`, база — `.guest-pilot-data/guest-pilot.db`. Начальная регистрация не требуется. `GET /api/v1/health` содержит `guestOnly: true`. По HTTP доступны только гостевые маршруты, страница помощника и её ресурсы. Чат и файлы идут через каналы WebRTC в открытом сеансе. Сервер останавливается по Ctrl+C.

Для постоянного стенда запустите пилот под отдельным пользователем со своим каталогом данных, прокси и экземпляром coturn. Если хост уже обслуживает другой EnotDesk, выделите пилоту свободные порты HTTPS, TURN и отдельный диапазон TURN relay. Пример ниже использует TCP 18443 для HTTPS и WSS, TCP/UDP 13478 для TURN и UDP 41000–41031 для TURN relay. Замените имена и адреса своими и откройте выбранные порты пилота в сетевом экране. Node.js остаётся на loopback.

| Переменная | Пример и назначение |
| --- | --- |
| `ENOT_PILOT_PUBLIC_URL` | `https://pilot.example.org:18443` |
| `ENOT_PILOT_TRUSTED_PROXY` | `127.0.0.1` при локальном прокси, выставляющем адрес клиента |
| `ENOT_PILOT_TURN_URLS` | `turn:pilot.example.org:13478?transport=udp,turn:pilot.example.org:13478?transport=tcp` |
| `ENOT_PILOT_TURN_SECRET` | Случайная строка от 32 символов, одна для Node.js и coturn |
| `ENOT_PILOT_HOST`, `ENOT_PILOT_PORT` | `127.0.0.1`, `17880` |
| `ENOT_PILOT_DATA_DIR` | Каталог базы пилота, доступный только его пользователю |

Храните секрет TURN в защищённых файлах среды и конфигурации. Проксируйте запросы по HTTPS, включая WebSocket `/signal`, на `127.0.0.1:17880`. Для отдельного поддомена получите сертификат с автоматическим продлением. Если 80 и 443 обслуживает другой экземпляр прокси, используйте DNS-01. DNS-имя TURN должно разрешаться в IP самого TURN-сервера.

В coturn задайте свой порт прослушивания, IP и диапазон relay, `realm` с доменом пилота, `use-auth-secret` и `static-auth-secret`. За NAT укажите отображение внешнего IP на внутренний через `external-ip`. Ограничьте число и пропускную способность аллокаций, запретите loopback, multicast и адреса внутренних сетей в качестве TURN-пиров. Сервер пилота выдаёт временные ключи обоим участникам после подтверждения подключения.

## Сборка и запуск клиента

Переносимые архивы Linux x64 и ARM64 доступны в [гостевом выпуске](https://github.com/Flint-sega/enotdesk/releases/tag/guest-pilot-0.6.30-2-linux). Перед распаковкой проверьте контрольную сумму из `SHA256SUMS.txt`. Новые сборки ветки `guest-edition` проверяет GitHub Actions. Для локальной сборки запускайте команды на Linux нужной архитектуры, чтобы пакет включал соответствующий нативный модуль ввода.

```sh
npm ci
npm run pack:linux -- dir --publish never
```

Запустите `enotdesk-guest-pilot` из папки подходящей архитектуры со всем её содержимым. При первом запуске введите общий HTTPS-адрес пилота в настройках обоих клиентов. Для локальной проверки адрес по умолчанию — `http://127.0.0.1:17880`.

Профиль EnotDesk Guest Pilot хранится отдельно. В клиенте пилота отключены штатное автообновление, регистрация обработчика `enotdesk://` и режим постоянного доступа.

## Приёмка через интернет

1. Запустите два клиента X11 с новыми профилями в сетях с разными публичными адресами. Проверьте, что форма помощника загрузилась по HTTPS с пилотного сервера.
2. Начните сеанс на первом клиенте и откройте приглашение во втором. Проверьте, что видео и ввод доступны только после явного согласия.
3. Проверьте, что выбранная пара ICE состоит из двух `relay`-кандидатов и TURN зафиксировал прямые подключения с обоих внешних адресов. WSS используется для сигналинга, клиентского моста до TURN нет.
4. Проверьте изменение видео, нативные клик и клавишу. Завершите сеанс с компьютера владельца и убедитесь, что помощник вернулся к форме и повторное применение ссылки отклоняется.
5. Повторите со сменой ролей с холодного старта. Зафиксируйте версии клиентских сборок, статистику декодированных кадров, выбранную пару ICE и завершение без передачи токенов или ключей в отчёт.
