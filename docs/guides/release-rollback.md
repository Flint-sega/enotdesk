# Откат выпуска (для сопровождающего)

Что делать, если выпущенная версия N оказалась плохой. Прецедент — v0.6.15 (10.10.2026): установщик при
обновлении удалял службу агента; v0.6.15 скрыта, исправление вышло в v0.6.16 (подробности — MANUAL-QA,
запись 10.10.2026 «ИНЦИДЕНТ v0.6.15»).

## Как устроены обновления (почему порядок именно такой)

- Программа берёт фид из `https://github.com/Flint-sega/enotdesk/releases/latest/download/` — это
  **последний опубликованный не-черновик** (`latest.yml`, `latest-linux.yml`).
- Обновление только вперёд: клиент, уже ставший версией N, к N-1 сам не вернётся.
- Страницы `/downloads` серверов отдают файлы из своего `ENOT_DIST_DIR` — их GitHub не трогает.

## Порядок

1. **Остановить распространение (минуты).** GitHub → Releases → vN → Edit → **«Save as draft»**.
   «Последним» снова станет N-1: клиенты, ещё не обновившиеся, на N не перейдут (фид vN исчезнет —
   проверьте `curl -sL …/releases/latest/download/latest.yml | head -3`). Ничего не удаляйте: черновик
   хранит файлы для разбора, тег остаётся в git.
2. **Вернуть сборки на свои серверы.** Если `/downloads` уже отдаёт N — верните файлы N-1 в
   `ENOT_DIST_DIR` (сверка с `checksums-sha256.txt` релиза N-1).
3. **Сервер, если выкатывался вместе с N.** Переключите `/opt/enotdesk/current` на прежний релиз и
   перезапустите сервис ([SERVER.md §5](../SERVER.md)). Если N изменил схему базы — восстановите базу из
   копии перед деплоем ([SERVER.md §7](../SERVER.md)).
4. **Исправление — новой версией N+1**, никогда не перезаливкой N (тег и файлы N неизменны: кто-то уже
   скачал их, и контрольные суммы должны сходиться). В N+1 — лечение тех, кто успел обновиться (для
   v0.6.15 установщик v0.6.16 пересоздавал удалённую службу).
5. **Проверить N+1 живьём** на машине, которая успела стать N (путь N → N+1), и на чистой N-1 → N+1.
6. **Опубликовать N+1** (тег `vN+1`), убедиться, что фид отдаёт N+1, обновить `/downloads`.
7. **Записать** в MANUAL-QA: что сломалось, кого задело, как вылечено. Судьбу черновика vN (оставить
   скрытым или удалить) решает владелец проекта.

## Чего не делать

- Не удалять тег и релиз N в первые минуты — потеряете доказательства и сломаете ссылки на файлы.
- Не выпускать «N-1 под новым номером» без причины — лучше исправление вперёд.
- Не включать понижение версии в клиенте (`allowDowngrade`) ради отката: это откроет путь подсунуть
  старую уязвимую версию.
