# EnotDesk — чек-лист ручной приёмки

> Что считается «готово» для выпуска 1.0 — [ACCEPTANCE-1.0.md](ACCEPTANCE-1.0.md) (матрица и условия, ADR 0037). Этот файл — журнал живых проверок и их протоколы.

Этот чек-лист — для живой приёмки на двух реальных машинах. Автотесты (500+ unit/server/client/hub)
не покрывают нативный ввод, WebRTC-медиу и поведение служб на живых ОС — здесь фиксируем именно это.

Правила:
- **Приоритет — Windows** (решение владельца: «Все три, приоритет Win»).
- Чек-лист **пополняется фазами**: после приёмки фазы добавляются новые пункты, старые не удаляются.
- Отметка `[x]` = проверено живьём, дата и результат (комментарий) обязательны. Пункт, который
  нельзя проверить — честно помечается «N/A + причина», не «пройдено».
- Подготовка: свежие сборки на обеих машинах (один и тот же билд), сервер развёрнут и доступен,
  админ + оператор заведены. Ссылки: `docs/AGENT.md`, `docs/BUILD.md`, `docs/SERVER.md`.

## Известные ограничения v1 (не дефекты при приёмке)

- Windows: session 0 — видео/ввод консольной сессии из службы недоступны (W-U7, docs/AGENT.md).
- Тост на экран: идёт только в активную консольную сессию; машина на экране входа — отказ `no-active-session` (W-U12). Второй тост заменяет незабранный агентом первый (у оператора, чей тост заменили, — «подтверждения нет»).
- Терминал: мост поднимается с `iceServers: []`, если `/rtc-config` недоступен или TURN не настроен — соединение только по LAN/напрямую; сквозной терминал через NAT — проверить вручную (W-U11).
- Windows: файловый лог службы — только по маркеру диагностики (`svc-diag.enabled` → `svc-diag.log`, потолок 1 МБ с ротацией; выключение — `windows-diag.bat off`); без маркера логов нет (W-U8).
- Агент v1 без tray-иконки — сознательное решение, управление через службу (W-U10).
- Wayland (Linux): управление вводом не поддерживается, честный статус в UI/логе.
- macOS: TCC для LaunchDaemon без MDM ограничен (M3).
- Сборки неподписаны: SmartScreen/Gatekeeper — обход по README (история 35).

## Прогон upgrade-v2 (новые фичи — живая приёмка)

- B3/B1/B2 — первый запуск: baked-адрес (сборка с `-c.extraMetadata.ENOT_BAKED_SERVER_URL=...`) → чип «Сервер доступен»; файл `enotdesk-server.txt` рядом с exe подхватывается; экран проверки показывает честный статус
- Инвентарь — heartbeat несёт ОС/версию/uptime/диск → панель «Машины» показывает; мусор отбрасывается
- Адаптивный битрейт — при потерях ≥5% видео ступенчато падает (2500→1200→600), при восстановлении растёт не раньше 15 с
- TOTP-2FA — включение (ENOT_SECRET_KEY задан, QR/секрет, 10 резервных кодов), логин с кодом, неверный код, резервный код, отключение с паролем
- Webhooks — session.started/ended + machine.claim.denied доходят с верной подписью; неверный секрет/URL → ретраи и тишина
- Терминал (W-U11) — живой сквозной прогон через NAT: iceServers из /rtc-config доезжают до моста
- Toast (W-U12) — живой WTSSendMessageW: тост в активной сессии; экран входа → no-active-session
- quick-setup — `scripts/quick-setup.sh` на чистой VM: bare-metal (с доменом и без: HTTP-предупреждение, DNS-подсказка), `--docker`, автоген-пароль показан один раз и работает, повторный запуск без `--update` честно отказывает, `--update` сохраняет секреты и подхватывает умолчания из env-файла

## EnotDesk Hub (живая приёмка)

Хаб (тикет-система + чат-виджет + one-click + email-канал, ADR 0023–0025) покрыт автотестами
на уровне API/швов; ниже — живая приёмка: реальный сайт, реальный почтовый ящик, три ОС.
Подготовка: сервер EnotDesk развёрнут, хаб включён и отдаётся наружу (bare-metal — юнит
`enotdesk-hub` за Caddy, docker — профиль `hub`), в консоли есть аккаунты admin и operator
(EnotDesk-аккаунты; SSO), виджет добавлен на реальный сайт. Консоль хаба — `/hub/`, админ-раздел
настроек — в ней же.

  ключится на правом (прокси-дописанном) hop, сменные фейки слева лимит не
  обнуляют.
- **P1 — сервер: глобальный потолок релея обходился chunked-загрузкой.**
  Потолок (relayMax×10) считался по декларированному `Content-Length`;

  декларацию (400) как защита в глубину. Тест: chunked → 411, обычный путь

- **P2 — mac-путь обновления сломан флагом.** MacUpdater не имеет quit-хука

  mac-фаза отложена, ВМ104). Win/linux — прежняя схема.
- **P2 — toast: rate-limit списывался до auth.** Аноним выжигал IP-бакет,
  общий с операторами за тем же egress. Переставлен после auth+RBAC, как у
  claim/wol. Тест: 10 анонимных → оператор не получает 429.
- **P2 — гостевые HTTP-эндпоинты виджета хаба без лимита.** Паритет с
  WS-гостем (20/10с) не выдержан — allowlist- origin ограничивает «кто», не

### 19.10.2026 — адаптивный битрейт машинного видео (ADR 0030 addendum): живой замер на лабовой Linux-машине

Стенд: лабовая Linux-ВМ (Debian 13, GNOME X11); на ней временный сервер 0.6.22 на loopback, временный агент — официальная сборка v0.6.22 с подменённым `bridge.mjs` (остальные файлы побайтно = исходникам), веб-оператор — headless Chromium через CDP; движение на экране — полноэкранный анимированный шум; потери — `tc netem loss 10%` на lo. - База: ~2,3–2,8 Мбит/с при движении на экране — верхняя ступень 2,5 Мбит/с — PASS.
- **Найден и исправлен дефект `client/lib/rtc-stats.mjs`** (существовал с ADR 0020, задевает и attended-хост): у отправителя `remote-inbound-rtp` не несёт `packetsReceived`, формула давала `lossPct = 100%` после первого потерянного пакета — лестница падала 2,5 → 1,2 → 0,6 и **не поднималась до конца сеанса** (замер до фикса: после снятия потерь 40+ с держится ~0,6 Мбит/с, `lossPct:100` при `fractionLost:0`). Фикс — `fractionLost` последнего интервала RTCP.
- После фикса: потери 10% → 1,2 Мбит/с через 2 с, 0,6 через 4 с — PASS; снятие потерь → 1,2 и через 16 с 2,5 Мбит/с — PASS.
- Наблюдение (не дефект, политика ADR 0020): при длительных потерях лестница раз в ~20 с пробует 1,2 по одному «чистому» интервалу и откатывается; кандидат на улучшение — подъём только после нескольких чистых интервалов подряд.

переподключение пайпа, отсчёт начинался только при его создании; исправлено (отсчёт и от начала сеанса).
`0.6.28-seed.2` (setup.exe /S поверх зачисленной машины): лабовый оператор на статичном экране — первый кадр
1280×800 через 1,5 с (`firstFrameMs` 1529), без единого движения мыши и клавиш (`kicks` 0); снимок — настоящий
рабочий стол. Попутно: тихая установка сбросила Environment службы (исправление — ветка `feature/win-update-keep-service`).

## 22.10.2026 — первый автопрогон помогаемой стороны (ветка `feature/acceptance-harness`)
Сборка pre `0.6.28-at.1` (портатив с авто-сеансом и авто-согласием) на Win10-ВМ стенда, запуск в сеансе пользователя
через планировщик: сеанс создан сам за 28 с, `auto-session.json` записан. Лабовый оператор (режим attended, отвечает
на offer хоста): «Оператор подключён», видео 1280×800 через 1,5 с, каналы input/chat/clip/file открыты, ввод выдан.
Находки:
1. **Переподключение оператора с новой страницы в течение грейса — чёрный экран.** Повторный claim того же
   оператора на живой сеанс сервер отдаёт как `resumed`, но хост не предлагает видео заново (его pc для этого claim
   считается живым) — новая страница оператора ждёт offer вечно. Так будет при перезагрузке страницы `/operator`
   в первые 30 с после обрыва. Чинить: оператор без живого pc просит у хоста новый offer (или сервер шлёт хосту
   `operator-joined` при новом WS того же claim). Живой /operator в браузере — подтвердить.
2. **Окно брандмауэра Windows на каждый запуск портативки** («Windows Defender Firewall has blocked some features»):
   портатив распаковывается во временную папку с новым именем, разрешение не запоминается. Видео работает и при
   «Отмена» (исходящие соединения). Нужна строка в инструкции клиенту; кэш распаковки по версии (решение Р15) уберёт
   повтор.
3. Перемещение курсора оператором на снимках не подтвердилось (курсор остался у «Пуска») — перепроверить с
   наблюдателем на ВМ (координаты курсора), прежде чем считать дефектом.

## 22.10.2026 — обновление Windows больше не стирает настройки службы (ветка `feature/win-update-keep-service`)
Находка на ВМ102 (тихая установка setup.exe поверх зачисленной машины): после обновления в Environment службы
`EnotDeskAgent` остались только значения по умолчанию — лабовый выключатель `ENOT_VIDEO_ATTACH=off` пропал.
Причина: обновление запускает деинсталлятор прежней версии, он удалял службу, а «лечение» установщика
создавало её заново со стандартным Environment. Исправление: при обновлении (`--updated`) служба только
останавливается; удаляется — лишь при настоящем удалении программы. Действует для обновлений С этой версии
(деинсталлятор — от установленной версии). Тест-контракт `packaging-contract`. Живьём — две установки подряд на ВМ.

## 22.10.2026 — повторный вход оператора в живой сеанс без чёрного экрана (ветка `feature/operator-rejoin-offer`)
Находка автопрогона (Win10-ВМ, сборка 0.6.28-at.1): второй вход оператора в тот же сеанс (новый claim по ID+паролю,
как при перезагрузке страницы `/operator`) — сервер отвечает `resumed`, offer от хоста не приходит, чёрный экран.
Трассировка: сервер шлёт хосту `operator-joined` и при claim, и при WS-аутентификации; offer на первый уходил, пока
WS оператора ещё не подключён, и отбрасывался; второй хост игнорировал. Исправление: повторный `operator-joined`
при pc без ответа или упавшем пересоздаёт pc с новым offer; живой pc не трогается.
Сборка pre `0.6.28-rj.1` (автотест-портатив) на той же ВМ: три входа подряд в один сеанс — каждый получает offer,
видео 1280×800 и соединение меньше чем за секунду. Автоматически: контракт рендерера, `npm test`, lint, смоуки.

## 22.10.2026 — сеансы через рабочий сервер под учёткой qa-auto (ветка `feature/turn-relay-range`)
Учётка `qa-auto` (роль operator) создана на рабочем сервере по решению владельца (ADR 0037, Р14); её сеансы видны в
истории. Помогаемая сторона — автотест-портатив на Win10-ВМ стенда (за домашним NAT), оператор — лабовый харнесс на
Mac. (1) Обычный ICE: сеанс через рабочий сервер, видео 1280×800 за 1 с, но пара host↔prflx (обе стороны в одной
домашней сети — через интернет шёл только сигналинг). (2) Принудительная ретрансляция (`iceTransportPolicy: relay`):
пара relay/udp ↔ srflx/udp через coturn рабочего сервера, RTT 78 мс, видео 1280×800 за 1,5 с, каналы и чат — PASS.
Ёмкость: в простое на сервере заняты 6 сокетов ретрансляции, во время одного сеанса — 11 → ~5 портов на сеанс с одним
оператором; диапазон 49160–49200 (41 порт) держит ≈7 одновременных сеансов. Установщик и docker-coturn расширены до
49160–49999 (~165 сеансов). На рабочем сервере — по слову владельца (`--reset-turn` + файрвол/группа безопасности).
TURN по TCP: с машины стенда (без VPN) `turnutils_uclient -t` к coturn рабочего сервера с эфемерными кредами — 12/12 пакетов (UDP — 11/12); с Mac разработчика сеанс с TCP-only ретрансляцией не поднялся — трафик Mac к серверу идёт через VPN (артефакт среды).
Не проверено: мобильный интернет (CGNAT), полный сеанс при закрытом UDP, стороны в разных домашних сетях — с владельцем (раздача с телефона).

## 22.10.2026 — рабочий сервер: диапазон ретрансляции 49160–49999
По слову владельца: на рабочем сервере (живых сеансов 0) `max-port` coturn 49200 → 49999 (бэкап конфига рядом),
перезапуск; конфиг читается службой, realm на месте. Файрвол самого сервера не мешает (ufw выключен, INPUT
ACCEPT). Проверка: три сеанса под `qa-auto` с принудительной ретрансляцией — порты ретрансляции 49426, 49546,
49910 (выше прежней границы), пара relay/udp ↔ srflx/udp, RTT 53–110 мс, видео за 1,3–1,8 с — PASS; значит,
хостинг эти порты снаружи не режет. Ёмкость теперь ≈165 одновременных сеансов с одним оператором.

## 22.10.2026 — хелпер видео: защита пайпа от подмены (ветка `feature/helper-pipe-hardening`)
Ревью безопасности ветки экрана входа (`.local`, отдельный агент) нашло P1, касающееся и выпущенных версий: пайп
хелпера имел фиксированное имя `\\.\pipe\enotdesk-video` и создавался без `FILE_FLAG_FIRST_PIPE_INSTANCE` — локальный
пользователь мог заранее создать пайп с этим именем, служба подключилась бы к нему, отдала hello-токен и весь ввод
оператора (на экране UAC/входа — пароли) и показала бы оператору поддельные кадры. Исправление: имя пайпа своё на
каждый запуск (`enotdesk-video-<32 hex>`, передаётся хелперу в `--pipe`), `FILE_FLAG_FIRST_PIPE_INSTANCE`; хелпер
выходит сам после конца своего сеанса и если за 60 с никто не аутентифицировался (осиротевший хелпер больше не висит,
в том числе от SYSTEM); установщик останавливает `enotdesk-video.exe` по имени; служба зовёт taskkill по абсолютному
пути; «уже установлено» для кнопки «Машина» — только exe внутри самой папки Program Files.
Автоматически: тесты video-host (имя пайпа на каждый запуск), agent-install, packaging; `cargo check` (windows-msvc).
Живьём — на стенде с тестовой сборкой: видео/ввод работают, в журнале хелпера `start` с новым именем, после конца
сеанса — `exit session-ended`; попытка занять старое фиксированное имя ничего не даёт.
