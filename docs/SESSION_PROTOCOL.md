# Протокол сеанса EnotDesk

Как стороны сеанса договариваются друг с другом: REST `/api/v1`, сигналинг WebSocket `/signal`, каналы
данных WebRTC. Описание сверяется с кодом тестом `server/test/session-protocol-doc.test.mjs`: новый тип
сообщения, код закрытия, причина завершения или канал без строки здесь — красный тест.

Участники: **хост** (клиент помощи в attended-сеансе; агент машины в unattended), **оператор**
(`/operator` в браузере или в окне приложения), **сервер**. Сервер пересылает только сигналинг; видео и
данные идут между хостом и оператором напрямую или через TURN.

## 1. Состояния сеанса

`waiting` → `pending-consent` → `approved` → `ended`.

- `waiting` — клиент зарегистрировал сеанс и ждёт оператора;
- `pending-consent` — оператор сделал claim, ждём решения хоста;
- `approved` — хост согласился: открыт сигналинг `signal`, ворота ввода хоста открыты;
- `ended` — конец, `end_reason` — одна из причин раздела 5.

## 2. REST (attended)

| Запрос | Кто | Что делает |
|---|---|---|
| `POST /sessions` | клиент (без входа) | Создаёт сеанс: `{hostId?, password?}` → `{sessionId, password, hostToken, expiresAt}`. 9-значный `hostId` — закреплённый ID ПК; прежний живой сеанс этого ID завершается (`superseded`). Лимит: 3 ждущих сеанса с адреса. |
| `POST /sessions/:id/claim` | оператор | `{password, contactId?}` по `sessionId` или `hostId` → `{sessionId, claimId, operator, state}`. Сеанс уже занят — присоединение вторым оператором (`joined: true`, свой `claimId`). |
| `GET /sessions/:id/connect` | оператор | Свой `claimId` для сеанса, закреплённого за оператором (one-click хаба, ADR 0024). |
| `POST /sessions/:id/decision` | хост (`hostToken`) | `{claimId, allow}` — согласие или отказ (`denied`). |
| `POST /sessions/:id/end` | хост или оператор | Завершить (`ended`; хост может передать `reason: "idle"`). |
| `GET /rtc-config` | хост или оператор | ICE-серверы: STUN/TURN с эфемерными кредами (HMAC от `ENOT_TURN_SECRET`, срок 1 ч). |

**Unattended:** `POST /machines/:id/claim` `{reason, pin?}` (оператор) создаёт сеанс сразу в
`pending-consent` и отдаёт `{sessionId, claimId, machineId, password}` — пароль нужен коллеге для
присоединения. Агент: `POST /agent/register` `{code, name}` → токен машины; `GET /agent/session` —
есть ли сеанс для машины; `POST /agent/heartbeat` — онлайн, инвентарь, сообщения и пробуждения. Агент
согласие даёт сам (`decision allow`): политику (причина, PIN) уже проверил сервер.

## 3. Сигналинг `/signal`

Одно соединение на участника. Первое сообщение — `auth`, без него за `authTimeoutMs` (5 с) соединение
закрывается.

- хост: `{type:"auth", role:"host", sessionId, token: hostToken}` (агент — токен машины);
- оператор: `{type:"auth", role:"operator", sessionId, claimId, token: <токен входа>}`.

Ответ — `ready` `{sessionId, role, state, graceMs}`. Затем сервер «доигрывает» то, что участник мог
пропустить: хосту в `pending-consent` — `claim`, в `approved` — `approved` и по `operator-joined` на каждого
подключённого оператора; оператору в `approved` — `approved`.

### Сообщения

| Тип | Направление | Смысл |
|---|---|---|
| `auth` | участник → сервер | Вход (см. выше). |
| `ready` | сервер → участник | Вход принят, текущее состояние и `graceMs`. |
| `claim` | сервер → хост | Оператор просит доступ: `{claimId, operator, reason?}` (`reason` — для машины). |
| `approved` | сервер → все | Хост согласился. |
| `operator-joined` | сервер → хост | Оператор подключился или переподключился: `{claimId, operator}` — хосту поднять для него свой pc. |
| `operator-left` | сервер → хост | Сокет оператора закрылся: `{claimId}`. |
| `signal` | хост ↔ оператор через сервер | `{data: {description: {type: offer|answer, sdp}} | {candidate}}`. Хост может адресовать `to: claimId`; от оператора сервер добавляет `from: claimId`. Только в `approved`, не чаще 150 за 5 с. |
| `heartbeat` | хост ↔ сервер | Хост продлевает аренду сеанса (`leaseMs` 20 с), сервер отвечает тем же; `termActive` — для журнала терминала. |
| `peer-reconnecting` | сервер → другая сторона | `{role}` потерян, идёт грейс. |
| `resumed` | сервер → участники | Потерянная сторона вернулась в грейсе. |
| `ended` | сервер → все | `{reason}` — сеанс окончен. |
| `idle-warning` | хост → операторы | `{remainingSec}` до завершения по бездействию. |
| `idle-clear` | хост → операторы | Бездействие снято. |
| `machine-video` | хост → операторы | Статус видео: у машины — видеохелпера, у клиента помощи — показа экрана (`reason: wayland-portal` — ждём выбор экрана в системном окне GNOME, `capture-denied` — захват не начался): `{state: spawning|connecting|running|error|off, reason?}`. |
| `file-link` | хост ↔ операторы | Ссылка на файл в резервном релее `/api/v1/relay/…` (`{name, size, url}`). |
| `error` | сервер → участник | `{code, message}` — ошибка без закрытия (например `not_approved`, `rate_limited`, `bad_signal`). |

### Коды закрытия

| Код | Причина |
|---|---|
| `1000` | `ended` — сеанс окончен (после сообщения `ended`) |
| `4000` | `replaced` — тот же оператор вошёл заново с другого сокета |
| `4001` | `auth-timeout` |
| `4002` | `auth-first` / `bad-message` |
| `4003` | `invalid-session` — нет сеанса, неверный токен, сеанс закончен или не в том состоянии |
| `4004` | `duplicate-socket` — второй сокет хоста |
| `4005` | `server-busy` — достигнут `ENOT_MAX_SESSIONS` |
| `1008` | `slow-consumer` — превышен лимит сообщений |

## 4. Грейс и обрывы (ADR 0013)

До согласия обрыв любой стороны завершает сеанс сразу (fail-closed). В `approved` у потерянной стороны
есть `graceMs` (по умолчанию 30 с, `ENOT_GRACE_MS`), чтобы вернуться с теми же токенами: другие получают
`peer-reconnecting`, по возвращении — `resumed`; не вернулась — `host-lost` или `operator-lost`. Хост,
который в `approved` не шлёт `heartbeat` дольше аренды, тоже считается потерянным: сервер объявляет грейс
и проверяет сокет пингом; сокет жив, а `heartbeat` так и нет — после 8 циклов `lease-expired`.

## 5. Причины завершения (`ended.reason`)

| Причина | Когда |
|---|---|
| `ended` | Хост или оператор нажал «Завершить». |
| `idle` | Хост завершил по бездействию оператора (30 мин, `ENOT_IDLE_MINUTES`). |
| `denied` | Хост отказал. |
| `host-lost` | Хост не вернулся в грейсе. |
| `operator-lost` | Оператор не вернулся в грейсе. |
| `lease-expired` | Аренда сеанса истекла: никто не пришёл (`waiting`, `pending-consent`) или хост в `approved` перестал слать `heartbeat`, хотя сокет ещё отвечает. |
| `superseded` | Тот же ПК начал новый сеанс. |
| `machine-revoked` | Машину отозвали. |
| `password-changed` | Оператор сменил пароль — его сеансы закрыты. |
| `totp-disabled` | Оператор выключил 2FA. |
| `operator-revoked` | Оператора отключили или удалили. |

## 6. Каналы данных

Каналы создаёт тот, кто шлёт offer (ADR 0014): в attended — хост, по набору на каждого оператора; в
сеансе машины — оператор. Всё входящее проверяется allowlist'ом и лимитами; решение о вводе принимает
только main хоста по реальному состоянию сигналинга.

| Канал | Сеанс | Формат |
|---|---|---|
| `input` | оба | События ввода — раздел 6.1; служебные сообщения управления — 6.2. |
| `chat` | оба | `{type:"chat", text}` (до 2000 символов). В сеансе машины — только от оператора (показывается сообщением). |
| `clip` | attended | `{type:"clip", text}` (до 100 КБ), только по явному действию. |
| `file` | оба | `file-meta` → `file-accept` / `file-reject` → двоичные куски по 64 КБ → `file-done`; файл до 200 МБ. В сеансе машины — только от оператора, в папку `EnotDesk Files`. |
| `term` | машина | Оператор → `in`, `resize`, `close`; машина → `opened`, `out`, `exit`, `error`. Один терминал на машину, 5 мин простоя — закрытие. |

### 6.1. События ввода (`input`)

| Тип | Поля |
|---|---|
| `move` | `x`, `y` — доли экрана 0…1 |
| `button` | `button`: left/right/middle, `down`, `x`/`y` (необязательно) |
| `key` | `key` из allowlist (`INPUT_KEYS` в `client/lib/protocol.mjs`; физические клавиши, не символы), `down` |
| `scroll` | `dx`, `dy` — строки, по модулю до 1000 |

Кроме событий оператор по `input` шлёт `{quality: high|medium|low}` (пресет видео машины) и
`{display: on|off}` (приватность: погасить или включить монитор машины Windows через видеохелпер).

### 6.2. Управление при нескольких операторах (ADR 0030, 0035)

| Тип | Направление | Смысл |
|---|---|---|
| `claim-input` | оператор → хост | Взять управление. |
| `release-input` | оператор → хост | Отдать управление. |
| `pass-input` | оператор → хост | `{to: claimId}` — передать управление коллеге. |
| `view-only` | оператор → хост | `{on}` — только смотреть. |
| `input-grant` | хост → оператор | `{granted}` — у вас ли управление. |
| `participants` | хост → операторы | Список: кто в сеансе, у кого управление, кто только смотрит. |
| `session-info` | хост → оператор | `{video:false, reason:"video-slots-full"}` — видеослотов (3) нет, доступны данные и управление. |
