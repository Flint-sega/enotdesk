# 05 — Браузерный оператор /operator

**Требования:** R05, R19i, R05.1–R05.4, R09
**Blocked by:** 02 (i18n — общий контракт-тест и строки)
**Зона:** `web/` (новое), `client/test/` (расширение контракта), `server/pages.mjs`/`app.mjs` (отдача страницы)
**Волна:** 2
**Status:** ready

## Что должно заработать

Оператор открывает `https://сервер/operator` в Chrome, входит своим аккаунтом,
подключается по ID/паролю клиента и ведёт сеанс: видео, ввод мышью/клавиатурой,
чат, буфер, файлы — без установки desktop-приложения.

## Из брифа, дословно

> «Оба (Рекомендую)» — desktop как основной плюс браузерный ·
> «браузер не хуже desktop по главным сценариям»

## Разделы спецификации

Истории 14–19; Решения §браузерный оператор; Границы (`web/`); Швы §3.

## Критерии приёмки

- [ ] Страница `/operator` отдаётся сервером только аутентифицированному оператору/админу; CSP аналогичен desktop
- [ ] `web/input-source.mjs`: DOM pointer/wheel/keyboard → события протокола через `keyFromCode(e.code)`; юнит-тест трансляции (synthetic events → allowlist-JSON)
- [ ] Подключение: login → session.claim → WS /signal (тот же протокол) → answer; ICE очереди и грейс-состояния обрабатываются
- [ ] Чат/буфер/файлы через те же DC-каналы; файлы — input + drag&drop
- [ ] Состояния ended/peer-reconnecting/resumed/error отображаются; RBAC аудитора — только чтение (403-и как в desktop)
- [ ] Playwright-smoke: логин + подключение к фейк-пиру (signing offer/answer) проходит; паритет-отличия браузера задокументированы (docs)
- [ ] i18n: страница на ru/en через словари
